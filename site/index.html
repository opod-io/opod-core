Apache-2.0 core control plane free tier, no key early access · v0.1.0

Serve open models on the GPUs you already own.

Opod turns a Kubernetes cluster, or a few Linux machines with GPUs, into OpenAI-compatible model endpoints. It packs models onto cards by measured VRAM, scales idle models to zero, rolls out changes with proof, and keeps serving when its own control plane is down.

Install with helm → Read the open-source core

No database, no message queue, no sign-up. Images pull anonymously from ghcr.io/opod-io for linux/amd64 and linux/arm64.

any Kubernetes ≥ 1.28

What you get

Two pieces with a clear line between them.

The runtime that answers requests is open source. The control plane that places, scales and governs it is a separate product you install into your own cluster. The runtime never needs the control plane in order to serve.

Opod core: the runtime

open source

One Go binary. opod up starts a leader; opod join adds a worker that drives an inference engine on its GPU.

  • OpenAI-compatible gateway: /v1/chat/completions, /v1/embeddings, /v1/models, streaming
  • API keys with per-key RPM/TPM limits, model allowlists and expiry; join tokens with per-node HMAC
  • Engines: vLLM, llama.cpp (including RPC sharding across machines), Ollama and MLX-LM
  • Load-balances one model across workers; routes by placement
  • A frozen /admin/v1 contract and a typed event stream, so anything can manage it
  • No telemetry. It never phones home.
Apache-2.0 · DCO, no CLA · github.com/opod-io/opod-core

Opod control plane: opodcp

free tier

One Helm chart. It runs each endpoint as a leader plus workers on Kubernetes, and gives you a console and an API over all of them.

  • Per-GPU VRAM ledger and packing placer, fed by measured VRAM
  • Endpoints as plans: engine, flags, replicas, autoscale, images pinned by digest
  • Verified rollouts that restore the previous plan on failure, plus one-click rollback
  • Autoscaling with scale to zero; the leader answers 503 + Retry-After while it wakes
  • API keys, guardrail webhooks, fallback target, audit log, usage facts and export, alerts
  • Local users or OIDC SSO with viewer, operator and admin roles, team scoping, backup and restore
Proprietary · free with no key up to 16 GPUs in one cell (chart 0.1.0 still enforces the earlier 8) · public images
Quickstart

From nothing to a first token.

Pick the path that matches what you have. The laptop path was re-run word for word against the public 0.1.0 chart on 2026-09-12; the others are the same commands we run on GPU cells.

EKS, GKE, AKS, k3s, RKE2 or any other Kubernetes at version 1.28 or later with a default StorageClass. Takes about two minutes when images are warm.

1

Label your GPU nodes

The chart's device plugins and VRAM probes schedule onto nodes with this label. If you use opodcp infra up (bare-machine path), this is done for you.

kubectl label node <gpu-node> opod.io/gpu-vendor=nvidia
2

Check the cluster (optional)

The chart runs the same preflight as a pre-install Job and refuses a half-install, so you can skip this step. Running it first shows every check with its fix.

docker run --rm --network host -v ~/.kube:/kube:ro \
  ghcr.io/opod-io/opodcp:0.1.0 preflight --kubeconfig /kube/config
3

Install the control plane

This installs one Deployment with the console embedded, a preflight Job, RBAC and per-vendor probe DaemonSets. It adds no databases.

export ADMIN_TOKEN=$(openssl rand -hex 16)
helm install opod oci://ghcr.io/opod-io/charts/opod --version 0.1.0 \
  -n opod --create-namespace --set admin.token=$ADMIN_TOKEN

kubectl -n opod port-forward svc/opod-opodcp 8080:8080
# console: http://127.0.0.1:8080  (sign in with $ADMIN_TOKEN)
4

Create an endpoint

In the console, go to Endpoints → New and pick a catalog model. Or use the API: leave the node out and the placer chooses a GPU with room.

export OPOD=http://127.0.0.1:8080
curl -s -X POST $OPOD/api/v1/endpoints \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"chat","model":"qwen2.5-0.5b-gguf",
       "plan":{"model":{"id":"qwen2.5-0.5b-gguf","engine":"llamacpp"},
               "workers":[{"replicas":1,"engine":"llamacpp"}]}}'
5

Wait for a real token, then chat

The state goes pending → converging → serving. serving is reported only after the leader has produced a token.

curl -s -H "Authorization: Bearer $ADMIN_TOKEN" $OPOD/api/v1/endpoints/<id>/status | jq .phase,.proof

curl -s -X POST $OPOD/api/v1/endpoints/<id>/gateway/v1/chat/completions \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5-0.5b-gguf","messages":[{"role":"user","content":"hello"}]}'

Inside the cluster, the endpoint is a plain OpenAI URL: http://opod-ep-chat.opod.svc:8080/v1. Expose its Service the same way you expose anything else.

This runs the same product on a laptop with a llama.cpp CPU worker. It is ideal for kicking the tyres, and it is also what our CI runs. It works on Apple silicon.

This path is for Linux machines with GPUs, SSH and no Kubernetes. opodcp infra builds a k3s cluster over SSH, labels every node by GPU vendor, and writes the kubeconfig. Nothing else is required on the machines.

1

Get the opodcp CLI

Signed binary downloads arrive with the first tagged release. Until then, the CLI ships inside the control-plane image. Copy it out on a Linux machine that can reach the others over SSH.

id=$(docker create ghcr.io/opod-io/opodcp:0.1.0)
docker cp "$id":/opodcp ./opodcp && docker rm "$id"
./opodcp version
2

Describe the machines

# machines.yaml
cell: lab
ssh: { user: ubuntu, keyFile: ~/.ssh/id_ed25519, sudo: true }
server: { name: cp-1, host: 192.0.2.10 }
agents:
  - { name: gpu-1, host: 192.0.2.11 }   # GPU vendor is detected on the host
  - { name: gpu-2, host: 192.0.2.12 }
3

Plan, build, check, install

./opodcp infra plan -f machines.yaml     # host facts + gate, changes nothing
./opodcp infra up   -f machines.yaml     # k3s server + agents over SSH, vendor labels
./opodcp preflight --kubeconfig ~/.opodcp/lab/kubeconfig

export KUBECONFIG=~/.opodcp/lab/kubeconfig
helm install opod oci://ghcr.io/opod-io/charts/opod --version 0.1.0 \
  -n opod --create-namespace --set admin.token=$(openssl rand -hex 16)

Then continue from step 4 of the Kubernetes path. Use --local when the server is the machine you are typing on.

Measured on a design-partner cell: infra up built a 9-machine cluster in 80 s, and preflight to first token on an A6000 took 127 s.

This path uses only the open-source runtime on a Mac or Linux box: no Kubernetes and no control plane. It gives you one OpenAI-compatible URL in front of the engine you already run.

1

Build it (Go 1.25+)

Prebuilt binaries arrive with the first tagged release. Building takes a few seconds.

git clone https://github.com/opod-io/opod-core
cd opod-core && go build -o opod ./cmd/opod
2

Run an engine and start a leader

Ollama is the simplest engine to start with. vLLM, llama.cpp and MLX-LM work too, and ./opod doctor tells you which one fits your machine.

# macOS: brew install --cask ollama && open -a Ollama
# Linux: curl -fsSL https://ollama.com/install.sh | sh
OPOD_DEFAULT_MODEL=llama-3.2-1b ./opod up
# prints the API URL and an admin key (sk-orc-…), shown once
3

Point your tools at it

curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Authorization: Bearer sk-orc-…" -H 'Content-Type: application/json' \
  -d '{"model":"llama-3.2-1b","messages":[{"role":"user","content":"hello"}]}'

./opod connect --list        # copy-paste config for Cursor, Aider, Continue, Codex CLI, Open WebUI…
4

Add a machine

./opod token create --node                           # on the leader
./opod join "http://<leader>:8080?token=<node-token>"   # on the new machine
./opod shard create <model> 2 --nodes a,b              # split a model too big for one box
Early usages

What people run on it today.

Each card is labelled honestly. ready means it is in chart 0.1.0 and proven on real hardware. early means it works but is proven narrowly. next release means it is merged but not yet in the published chart.

A private OpenAI endpoint for your team

ready

Point Codex CLI, Aider, Continue, Open WebUI or the OpenAI SDK at your own GPUs. Give each person a key with RPM/TPM limits. The leader enforces keys even if the control plane is down.

curl -X POST $OPOD/api/v1/endpoints/<id>/keys \
  -d '{"name":"alice","rpmLimit":120}'

Pack several models onto one GPU

ready

Most internal models are small. Give each worker a VRAM budget and the placer packs them best-fit against the card's measured free memory. A plan that doesn't fit is refused with the measured number.

"plan": { "colocation": "shared",
  "workers": [{ "vramBudgetGb": 6,
                "engine": "llamacpp" }] }

Scale idle models to zero

ready

Set a floor of 0 and a ceiling. Idle endpoints release their GPUs; the first request wakes one worker, while the leader answers 503 with Retry-After. Measured wake from zero: 54 s with llama.cpp.

"autoscale": { "floor": 0, "max": 3,
  "targetInflight": 4, "idleSeconds": 600 }

Change models, flags or images safely

ready

A rollout validates, applies, waits for convergence, probes, then sends a smoke chat, and records a proof at every step. If any step fails, the previous plan is restored. Rollback is one call.

POST /api/v1/endpoints/<id>/rollouts   # body = new plan
POST /api/v1/rollouts/<id>/rollback

Govern it like production

ready

Add guardrail webhooks before each request and a fallback target when capacity is gone. You also get an audit log of every state change and alert rules that notify Slack, PagerDuty, Alertmanager or a webhook. Usage facts export to CSV, Parquet, ClickHouse or S3.

Front a hosted model with the same controls

ready

A remote endpoint is a leader with no GPU. It proxies an OpenAI-compatible vendor with a write-only key, and gets the same keys, limits, guardrails, audit and usage facts as your own models.

"model": { "source": "remote",
  "remoteUrl": "https://api.vendor.example/v1" }

Find idle GPUs before you install anything

ready

This is a read-only report on any cluster. Probe pods run in a throwaway namespace and are removed afterwards. No licence or install is needed.

opodcp audit --kubeconfig ~/.kube/config \
  --duration 5m --price 2.50

A model bigger than one machine

early

A llama.cpp pipeline-parallel gang across GPU nodes, placed and healed as one unit. It has been proven with a two-node gang on consumer GPUs. Tensor parallelism stays inside one machine by design.

Advantages

Why teams pick opod over assembling it themselves.

You could wire up vLLM, a gateway, KEDA, a metrics stack and a rollout system yourself. Opod gives you that as one install, with a few properties that are hard to get from parts.

Never on the request path

The control plane writes policy into files the leader mounts: the plan, keys and guardrails. Kill it and every endpoint keeps serving, enforcing keys and recording usage. This was proven by killing it during load.

Measured, not assumed

VRAM comes from the vendor probe on the node, load from the leader itself, and GPU-seconds from pod lifetimes. "Serving" means a token came back. When a number isn't measured, the console says so.

More models per card

Kubernetes hands out whole GPUs. Opod's ledger packs several models onto one card under explicit VRAM budgets, and refuses an overcommit with the number it measured.

Nothing extra to operate

SQLite on a volume, an in-process event bus and /metrics are all built in. On day two, helm upgrade --set connects the Postgres, ClickHouse, NATS, OIDC, Vault or KEDA you already run.

Your cluster, your network

Opod runs on any Kubernetes, or builds k3s on bare machines over SSH. Licence keys are verified offline. There is no phone-home and no remote kill switch, so it works air-gapped.

No lock-in on the wire

Clients speak the plain OpenAI API, and usage leaves as open formats. Endpoints are ordinary Deployments and Services with opod.io/* labels. The runtime underneath is Apache-2.0.

Pinned and reproducible

Every image in a plan is resolved to a digest when the plan is written and changed only by a rollout. No pod silently picks up a moved tag.

Honest when things break

Alerts are persisted and carry a remedy. Pods stranded on a lost node are swept, and an endpoint that can't converge reads degraded with the reason instead of pretending to be Pending.

Fair free tier

The full product is free up to 16 GPUs in one cell. Beyond that, only new placements are refused, with the remedy. Running workloads are never stopped, and an expired key never kills anything.

How it works

One endpoint is one leader and its workers.

Each endpoint serves one model identity inside one cluster. Requests go from your client to the endpoint's Service, then to the leader and a worker. The control plane sits beside that path: policy flows in as mounted files, and events and usage flow out through a cursor the control plane pulls.

If the control plane dies

Endpoints keep serving from their mounted plan and keys. Usage events wait in a bounded buffer in the leader until the control plane pulls them again.

If a leader dies

Kubernetes restarts it, workers re-join, and the endpoint re-converges. We measured about 60 s, including sharded endpoints.

If a worker or node dies

The pod is replaced and the ledger claims are released. Pods stuck on a lost node are swept after five minutes, and the endpoint reads degraded until it heals.

Straight talk

What is not there yet.

This is early software. Here is what we know you will run into, so you don't have to find it yourself.

  • No signed release yet. The first tagged release brings signed binaries, SBOMs and a signed chart. Until then, images are pinned by digest when a plan is written.
  • Serving is proven on NVIDIA. AMD is measured and placeable, but its worker image is not published yet. Intel and Tenstorrent are inventoried only.
  • Two engines in the control plane: vLLM and llama.cpp. SGLang is merged for the next chart. Ollama and MLX-LM are available in core only.
  • Shared packing is not a security boundary. VRAM budgets keep models from colliding, not tenants from each other. Use dedicated (the default) for untrusted neighbours.
  • One control-plane replica in 0.1.0. High availability on Postgres lands in the next chart.
  • The free tier is 16 GPUs, but chart 0.1.0 still enforces the earlier 8. The next chart carries 16. Running workloads are never affected either way.
  • Usage facts, not invoices. Opod exports what happened; pricing and showback are left to your FinOps tools.
  • OpenAI API only. The Anthropic Messages, audio and rerank shapes are out of scope for core.
FAQ

Questions people ask first.

Is opod open source?

The core runtime (opod) and the SDK are Apache-2.0 with no usage limit. The control plane (opodcp) is proprietary. Its images are publicly pullable, and it is free with no key up to 16 GPUs in one cell. The runtime never depends on the control plane: you can run core on its own, or manage it with your own tooling through /admin/v1.

Do I need Kubernetes?

For the control plane, yes: Kubernetes is its only executor. If you don't have a cluster, opodcp infra up builds k3s on your Linux machines over SSH. The core runtime alone needs no Kubernetes and runs on a Mac or Linux box.

Does traffic flow through the control plane?

No. Clients call the endpoint's Service, and the leader answers. The control plane writes the plan, keys and guardrail rules into a Secret the leader mounts, and pulls events and usage from the leader. Its console includes a playground proxy for convenience, but your applications never need it.

What happens above the free tier, or when a key expires?

The free tier is 16 GPUs in one cell (chart 0.1.0 still enforces the earlier 8; the next chart carries 16). Only new placements beyond the licensed number of GPUs are refused, and the refusal includes the remedy. Running workers are never stopped. An expired key keeps its ceiling through a grace period, then the free tier applies to new placements. Keys are verified offline against a public key built into the binary.

Does anything phone home?

No. Core has no telemetry. The control plane needs no connection to us: there is no licence server and no remote kill switch. It needs to reach your registry and model hub (or your mirrors) to pull images and weights.

Which models can I run?

Anything in the catalog (Qwen, Llama, Gemma, GLM, DeepSeek, gpt-oss, Mistral, Phi, vision and embedding models), or a Hugging Face GGUF or safetensors repo you add. Sizing is up to you: the ledger tells you what fits on each card before anything is scheduled.

Can I pack models on AMD, Intel or Tenstorrent cards?

The ledger places on any card whose VRAM is measured, which today means NVIDIA and AMD. Serving is proven on NVIDIA. AMD is waiting on its worker image, and Intel and Tenstorrent are inventoried only. We use those three words on purpose, because each one is checkable.

How do I remove it?

helm uninstall opod -n opod removes the control plane. Endpoints are ordinary Deployments and Services labelled opod.io/endpoint; delete them from the console first, or remove them by label. opodcp infra down uninstalls a k3s cluster that opod built.
